# aigowosyom

Worldbuilding data suite. Everything runs locally from one Node server.

| URL | What |
| --- | --- |
| `/` | Landing page |
| `/search?q=` | Site-wide search: dictionary, lore and calendar notes |
| `/calendar` | Tanakōdeyam calendar with per-day notes |
| `/lore` | Lore encyclopedia: categories, pages, search |
| `/lore/editor` | Lore editor (categories and pages, visual rich-text editor) |
| `/dictionary` | Public dictionary: browse languages, entry pages, search |
| `/dictionary/editor` | Dictionary editor (languages and words) |

## Run

```bash
npm install   # first time only
npm start
```

Node 20 or newer is needed (tried on Node 22 and 26). The one dependency with a compiled part is `better-sqlite3`, and it is built for the version of Node that installed it: **after updating Node, run `npm rebuild better-sqlite3`** (or `npm run rebuild`) in the project folder. Without that, the server says so and stops (it would otherwise complain about a `NODE_MODULE_VERSION` mismatch).

Then open <http://localhost:3000> (set `PORT` to change it). The server only listens on localhost.

## Data

Everything lives in one SQLite file, `data/worldbuilding.db` (created on first run, git-ignored). Back it up by copying that file while the server is stopped (or copy the `-wal`/`-shm` files alongside it if the server is running).

- **Calendar notes** are keyed by civil day number (days since 1970-01-01 UTC), so they stay attached to the same real day even if the calendar's parameters are later recalibrated.
- **Dictionary:** a `languages` table and a single `words` table (with `language_id`), plus `senses`, `word_variants` (same-language dialectal/spelling variants), `word_ancestry` (links to words in any language) and an FTS5 search index. Created/updated timestamps are stored but not shown.

## Dictionary notes

- **Public pages** are rendered by the server from the database on every request, so edits in the editor appear immediately.
- **Entry URLs:** `/dictionary/<language-slug>/<headword>`. Homographs (same spelling, same language) share one page as "Etymology 1, 2, …".
- **Links in text:** in definitions, etymology notes and ancestry notes, write `[[word]]` (same language), `[[slug:word]]`, or `[[slug:word|display text]]`. Links to entries that don't exist yet are shown in red.
- **Search** matches headwords, sinographs and English definitions, ignores diacritics (`o` finds `ō`) and matches prefixes. An unambiguous exact headword match goes straight to its entry.
- **Live suggestions:** the search box in the top bar shows matching entries (with their language) as you type; arrow keys and Enter work, and without JavaScript it still submits to the results page.
- **Statistics:** each language page has a Words / Statistics tab (`/dictionary/<slug>/?view=stats`): average and median letters per word, consonant : vowel ratio (Latin letters only, `y` counts as a consonant), parts-of-speech pie, word-length histogram, letter frequency, gender split, etymological sources and influence on other languages, and entry completeness. Letters are counted on the diacritic-folded headword, so digraphs like `kh` count as two.
- **Language colors:** each language can be given a color in the editor's language settings (a color picker with a "use default gray" button). The color is used for its badges everywhere (search results, suggestions, ancestor links, the family graph), for the accent band and heading chip on its pages and entries, and for the editor's accents. Languages without a color are gray; text on the badge switches between white and near-black for readability.
- **Language family tree:** `/dictionary/family` draws languages as nodes, ancestors above descendants. Generations follow *inherited* links; a language with no inherited parent sits below the languages it *borrows* from; other borrowed links and *areal* links are drawn as cross-links (solid, dashed and dotted lines respectively). Numbers and line thickness show how many words are linked. A relationships table below the graph lists the same data.
- **Variants** are one level deep: only a base word can be given variants, so a variant can't be chosen as a parent and a word that already has variants can't itself become a variant. This makes variant loops impossible. (Links created before this rule existed are left alone.)
- **Sound patterns:** a third language tab (`?view=sounds`) with a letter-pair heatmap. Each cell counts how often one letter is immediately followed by another in headwords; the `#` row and column show which letters begin and end words, and blank cells never occur. Vowels come first, then consonants (`y` counts as a consonant), so the vowel/consonant structure shows up as quadrants. It is based on spelling (a digraph like `kh` is k then h). Accented letters can be merged with plain ones or kept distinct (`&marks=keep`). Also shows the share of letter pairs that never occur, letters that never begin or end a word, and a ranked list of the most common pairs.
- **Sorting the Words tab:** alphabetical (with an initial-letter filter) or by part of speech (grouped, alphabetical within each group, with a part-of-speech filter). The sort and filter are kept while paging.
- **Parts of speech** are free text with suggestions in the editor, including *proper noun*, *personal name*, *family name* and *toponym*.
- **Random word** is also available on every entry page (a random word in that entry's language, never the same word again if there is another).
- **Typography:** words of the constructed languages are always sans-serif; everything else is serif; level-1 headings are exempt and use the sans stack. Mark a language word in markup with `class="conlang"`. The fonts live in `public/assets/site.css` (`--font-serif`, `--font-sans`).
- **Editor word list** can be sorted alphabetically or by last updated (your choice is remembered).
- **Alphabetical order** is by headword with diacritics folded and lowercased.
- **Reserved slugs:** `editor`, `search`, `random`, `family`, `api`.
- **Random word:** `/dictionary/random` (any language) or `/dictionary/random?language=<slug>`, linked from the dictionary home and each language page.
- **Proto-languages** are ordinary languages flagged "reconstructed"; their headwords display with a leading `*`.
- **Gender** (masculine/feminine/neuter) is only offered for languages flagged "has grammatical gender".

## Lore notes

- **Structure:** categories are the backbone; every page belongs to exactly one category. URLs are `/lore/<category-slug>/` and `/lore/<category-slug>/<page-slug>`. Pages are created and edited from a category's view in the editor, and can be moved to another category from the page form.
- **Page slugs** are generated from the title (accents and punctuation removed, e.g. "The Fall of Kyōra" becomes `the-fall-of-kyora`, with `-2`, `-3`… added if taken) and can be edited. Renaming a page keeps its URL unless you change the slug. Category slugs reserve `editor`, `search`, `random` and `api`.
- **Visual editor:** page bodies are written in a rich-text editor (headings 2–4, bold/italic/underline/strike, bulleted and numbered lists with nesting, quotes, links, horizontal rules, tables with row/column tools, undo/redo). Bodies are stored as sanitized HTML: the server keeps only an allowlist of tags and attributes and drops scripts, event handlers, `javascript:` links and the like, no matter what the editor sent. Pasted content is reduced to the same allowed formatting. Images are not supported yet.
- **Links:** `[[category]]` links a category, `[[category|Page Title]]` a page (matched by title or slug), and `[[category|Page Title|display text]]` adds display text. Dictionary links work in lore text too (`[[tanako:moin]]`, `[[tanako:moin|display]]`), and lore links work in dictionary text. Where a dictionary-style `[[word|text]]` link starts with the slug of an existing lore category, it is read as a lore link. The editor's `[[ ]]` button searches pages, categories and dictionary words and inserts the link for you; selected text becomes the display text. Links to pages that don't exist yet are shown in red.
- **Search:** a search box with live suggestions (titles and body text, diacritics ignored); an exact title goes straight to its page. `/lore/random` (optionally `?category=<slug>`) goes to a random page; random buttons are on the lore home, category pages and article pages.
- **Cross-links with the dictionary:** when a lore page has the same name as a dictionary entry, each links to the other: lore pages show "In the dictionary: …" and dictionary entries show "In the lore: …". Matching ignores case and diacritics (so *Kyōra* matches *kyora*) and also tries "headword + sinographs", so an era page titled "Niwosara 新雨" matches the entry *Niwosara* whose sinographs are 新雨.
- **Eras:** `public/calendar/eras.json` (the file the calendar reads) lists each era as `{ "name": "Niwosara", "sinographs": "新雨", "startYear": 1591 }`. The calendar shows name and sinographs together; everywhere else (lore pages, dictionary headwords) the name stands alone and the sinographs go in the dictionary's sinographs field. (An older file with the gloss glued to the name is split automatically.) A built-in **Eras** category holds one page per era, in chronological order; "Later …" entries (e.g. Later Kemairyom) get no page or entry. Pages are created automatically on startup and whenever `eras.json` changes, with the text "An era succeeding X and preceding Y, lasting a total of N years." (an era lasts until the year the next era in the file begins). The body is editable, and your edits are never overwritten by later syncs. Era titles come from `eras.json`, the slug and category are locked, era pages can't be deleted, and the Eras category can't be renamed or deleted (its color and description can be edited). If an era disappears from `eras.json`, its page becomes an ordinary page.
- **Era entries in the dictionary:** each era also gets a dictionary entry (proper noun) in the language *Tanakōdeyam*: the headword is the era name, the sinographs field holds the gloss, and its definition links to the era's lore page (it also gets the automatic "In the lore" link, since the names match). These entries are read-only in the editor and API and can't be deleted, except for their **etymology notes**, which you can edit (a re-sync from `eras.json` never overwrites them). The language is created automatically (slug `tanakodeyam`); if you already have a language with that slug or named "Tanakōdeyam" it is used instead, and it can't be deleted.
- **Calendar notes on era pages:** below the body (on the public page, and read-only below the editor) each era page lists every calendar note that falls within it, in date order, grouped by year (years without notes are skipped). Years are labelled the way the calendar counts them within the era, e.g. "Kemairyom 34" (hover for the universal year), and the page shows the era's span as "Kemairyom years 1–34". Each note shows its date as the English month name ("Second month 5") — except the two intercalary periods, which keep their native names (Hiūnmoin, Newōsēpreya) — with the Gregorian date faded beside it. A year shared by two eras (the year one ends and the next begins) appears in both, labelled with each page's own era. The calendar's date arithmetic is mirrored on the server in `lib/calendar.js`; keep it in step with `public/calendar/index.html`. The calendar also opens a given year via `/calendar/?year=2026`.
- **Books:** a built-in **Books** category (created automatically, like Eras: its name and slug are fixed and it can't be deleted; its color and description can be edited). Each page in it is a book — create them in the lore editor like any other page (the buttons say "New book"). A book's own text is optional and blank by default; a blank book shows nothing above its notes. Calendar notes are assigned to a book from the calendar: the note form has an optional **Book** dropdown (a note belongs to at most one book; "— none —" by default), and a note that has a book shows a 📖 link to it. A book's page lists its notes below its text exactly like an era page's notes: grouped by year (years without notes are skipped) in date order, with era-name-and-year headings ("Niwosara 10", or "Year N" before the first era), English month names, and the Gregorian date faded. The editor shows the same list read-only under the body. Era pages show a 📖 link on notes that belong to a book. Deleting a book, or moving its page to another category, keeps the notes in the calendar but unassigns them. API: `GET /api/lore/books` lists the books; `book_id` (or `null`) on `POST`/`PUT /api/notes` assigns a note, and leaving it out of an update leaves the assignment unchanged.
- **Category colors** work like language colors: a color picker in the category dialog (gray by default) tints badges, cards and the accent band on that category's pages.

## Calendar notes

- **Era + year controls:** under the "Universal year" box at the top of the calendar there is an **Era** dropdown and a **Year** number box (with a Go button; Enter works too) to jump to, say, *Kemairyom 10*. The controls show the era and number of whatever year is displayed; the year is the era's start year plus the number minus one, so *Year 1* of an era is the year it begins. A year shared by two eras (e.g. 2050) reads as the later one when you jump by year number, but jumping by era keeps the era you picked.
- **Links to a note:** search results, the note lists under era and book pages, and the lore editor link to `/calendar/?year=…&day=…&note=…` (`calendarUrl()` in `lib/notes.js`). The calendar opens that year, opens the day's notes and outlines the note; if the note has since been moved or deleted it just shows the day, and a link with only `?year=` still opens just that year.
- **Move a note to another date:** each note in a day's dialog has a ☰ menu with **Move to date…**. The dialog opens on the note's own **Day**, **Month** and **Year**, so moving it to another year means changing only the year; the day and month can be changed too (even within the same year). The year can be entered as era + number or as the Gregorian-based year number, and the boxes fill each other in. A live preview shows exactly where the note will land (calendar date, era year and Gregorian date). Months differ in length from year to year (the cut-off months Liāmoin and Elendāmoin and the two intercalary periods especially), so a day past the end of the chosen month is shortened to its last day (the preview says so), and a month that has no days in the chosen year (e.g. Newōsēpreya in 2018) can't be used. A note's book assignment is kept. API: `PUT /api/notes/:id` accepts an optional `day` (civil day number) to move a note.
- **Move all notes from a year:** the **Move a year's notes…** button next to Jump and Print opens a dialog with a *From* year (the year on screen by default) and a *To* year, each entered as era + number or as a Gregorian-based year. Every note in the first year moves to the same month and day-in-month of the second. The dialog previews the move before you confirm: how many notes will move, which will be shortened to a month's last day, and which won't move because their month has no days in the new year (those stay where they are). The move is one all-or-nothing step on the server, and afterwards you can jump to the target year. API: `POST /api/notes/move-year` with `{ "from": 2017, "to": 2026 }`; add `"dryRun": true` to preview without changing anything. The placement rule lives in `planDayInYear()` in `lib/calendar.js` and is mirrored by `planMove()` on the calendar page; keep them in step.

## Site-wide features

- **Top bar:** a slim bar along the top of every page links to the top page of each section (Calendar, Lore, Dictionary), highlighting the section you are in, with the theme switcher at the far right. It is hidden when printing. Pages rendered by the server get it from `siteBar()` in `lib/render.js`; the home page and the calendar page (hand-written HTML) carry a copy of the same markup. The calendar page has a "← Home" link above its title, since the bar no longer has a home link.
- **Themes:** the **Theme** dropdown in the slim bar switches the look of the whole site: *Default*, *Default (dark)*, *Neumorphic* and *Neumorphic (dark)*. The choice is kept in this browser (`localStorage`, key `aigowosyom.theme`) and applied before the page paints. *Default* is the original look. *Neumorphic* is a plain-CSS port of the soft raised/pressed style of [Neumorph.scss](https://github.com/ChemaAlfonso/neumorph.scss) (MIT): one shared background, light and dark shadows, gold hover/active text, with language and category colours kept. A theme puts two attributes on `<html>`: `data-theme` (the look: `default` or `neumorph`) and `data-mode` (`light` or `dark`). Files: `public/assets/theme.js` (list of themes, switcher, early apply), `public/assets/themes/neumorph.css` (every rule scoped to `html[data-theme="neumorph"]`, so Default is untouched) and `public/assets/themes/dark.css` (both dark modes, screen only: printing always uses light colours). The neumorphic look is built on CSS variables, so its dark mode only swaps the palette; Default (dark) recolours the site's variables and the few surfaces that hard-code a light colour. To add a theme: add it to `THEMES` in `theme.js`, write its stylesheet, and link it in `layout()` in `lib/render.js`, `public/index.html` and `public/calendar/index.html`.
- **Icons:** buttons and links that need a small picture (undo/redo, indent/outdent, remove, the note menu, random, book, lock, "opens in a new tab") use inline SVG icons from `public/assets/icons.js` instead of symbol or emoji characters, which older systems often have no font for. The file works in the browser (`Icons.el("undo")`) and on the server (`Icons.svg("dice")`), and the icons take the colour and size of the surrounding text. Plain arrows and bullets that every font has (← → ↑ ↓ • ×) are still ordinary text. Add an icon by adding its paths to `PATHS`.
- **Fonts:** language words are Helvetica (sans-serif) and everything else is Times New Roman (serif), set in `--font-sans` / `--font-serif` in `public/assets/site.css`. Other platforms fall back to Arial / Times-compatible fonts, with Noto and Japanese fonts behind them for the sinographs. This holds in every theme.
- **Site-wide search:** a search box under the section cards on the home page searches the dictionary (headwords, sinographs, definitions), the lore (titles and text) and the calendar's notes (titles and text), ignoring case and diacritics. Live suggestions show a mixed list as you type (arrow keys and Enter work); submitting opens `/search?q=…`, which groups results by section with a "See all →" link into each section's own search. Calendar-note hits show their era and year (e.g. "Kemairyom 10"), month and Gregorian date, and link to that year in the calendar. Notes are indexed by an FTS5 table kept in step with the `notes` table by database triggers.

## Maps

Interactive maps, drawn with [OpenLayers](https://openlayers.org/) (BSD-2, shipped as one file in `public/vendor/ol/`, no build step). A map is a flat plane of "map units" (not a real-world projection); the public page is `/maps` and the editor is `/maps/editor`. Everything in the editor is saved as you do it, and each map can be created, edited and deleted like a language or a lore category.

- **Layers.** *Geography* (land, lakes, rivers; independent shapes) and *States* (political units), plus names and places. States have dotted borders and a light shading in their color; all colors come from `--map-*` CSS variables in `public/assets/maps/maps.css`, so every theme and dark mode restyles the map, and labels use the site's serif font (or sans for a state whose name is a language word).
- **States share their borders.** Every corner of every state is a row in the database, and a state is a ring of corners, so two neighbours that touch use the *same* corners along their common border: dragging a corner moves it for both, with no gaps or overlaps. Drawing a state, clicking a neighbour's corner or border shares it (a corner is added to the neighbour's border too); with *Follow a neighbour's border* on, clicking two corners on the same border fills in the corners between them. *Edit borders* drags corners, welds a corner onto another by dropping it there, adds a corner by double-clicking a border, and removes one with Alt-click (refused if a state would be left with fewer than three corners). A state can have several pieces (*Add island*) and holes (*Add hole*).
- **States and the lore.** Every state has a page in the built-in **States** lore category, created with it, named after it, and kept in step (like the Eras): its text is written in the lore editor, its name and deletion are handled on the map. Deleting a state asks whether to delete its page too (otherwise it is kept as an ordinary page); clicking a state on the public map shows the start of its page and a link to it, and the page links back to the map.
- **Superstates.** States can be grouped into larger states, to any depth. Shift-click (or Ctrl-click) several states on the map or in the *States* list, then **Combine into a new state…**, or **Add to a superstate…** to put them in one that exists. The states keep existing, with their own shapes and pages; a superstate has no shape of its own (it is the sum of its clients: a heavier outline in its own colour around them, and its name over them when zoomed out). A superstate exists only while it has clients: when the last one is taken out or deleted it disappears (its lore page is kept as an ordinary page), and *Dissolve* removes just the grouping. In the lore a superstate is a state like any other (a page in the States category), and its page lists its clients automatically, as a nested list; a client's page says what it is part of. On the public map the list of states is a tree, and a superstate's panel lists its clients. When publishing, a superstate whose clients are all left out is left out too, with its page.
- **Elevation.** Land is divided into square cells, a mile on a side by default (a very large map gets bigger cells so the grid stays at about 2.5 million cells or fewer; the panel says the cell size), and every land cell has an elevation in feet. When land is first drawn it is a *plains* landscape: from the sea the land rises inland (quickly at first, then ever more slowly) to a plateau of about 900 ft, with gentle undulations that grow with distance from the coast. Cells that later become land (new or reshaped land) get plains too, cells that stop being land are cleared, and hand edits elsewhere are kept; the grid follows the size of the map. *Start over as plains…* regenerates everything with your own plateau height, rise distance and ruggedness. Elevation can be drawn three ways, which can be combined: **grayscale** (lighter is higher), **colours** (a ramp from green lowlands through yellow and tan to brown, grey rock and white peaks), and **relief shading** (hillshading, lit from the north-west, which shows ridges and valleys; on its own it is a neutral relief). They are the *Elevation* selector and *Relief shading* checkbox in the editor's Layers box and above the public map; your choice is remembered, and the height under the pointer is shown in a corner. Elevation is published with the map.
- **Elevation tools** (in the *Geography* group of the editor's tools). *Raise / lower*: press on the land and drag up to raise it or down to lower it; the land around the grabbed point is pulled along, by the **brush size** (in miles), with **sharpness** from soft hills (a broad smooth bump) to sharp mountains (a narrow peak with steep sides), and a **drag sensitivity** in feet per pixel. The effect is worked out from the land as it was when the drag began, so you can pull back and forth freely; the height at the grabbed point is shown as you drag. *Smooth* paints over the land to even it out. Edits are saved when you let go. The grid is stored compressed in the database (`lib/elevation.js`; the editor and viewer download it from `/api/maps/:id/elevation`). Brush strokes can be undone and redone (see below).
- **Undo and redo.** The editor's **Undo** and **Redo** buttons (top of the tools; Ctrl+Z, and Ctrl+Shift+Z or Ctrl+Y) step back and forward through up to 40 changes to a map's drawing: shapes, states, corners, groupings and statuses, places, and elevation brush strokes. Each button says what it would undo. Drawing a state, including the corners it adds on a neighbour's border, is one step. How it works: after each change the editor compares the map's drawing with how it was; a difference is a step, and undoing asks the server (`POST /api/maps/:id/restore`, `restoreMap()` in `lib/maps.js`) to put the earlier snapshot back with the same ids, so later steps stay valid. Elevation is put back with the land (a land change keeps the grid as it was), and a brush stroke is undone from the cells it changed. A state that goes away keeps its lore page (detached) if the page has text, and takes the page back if the state returns. While a state is being drawn, Ctrl+Z takes back the last corner. Not covered: map settings, tracer images, creating or deleting maps, and switching maps (which starts a fresh history).
- **Land joins up.** New land drawn with *Draw land* that overlaps, or shares a stretch of border with, land that is already there becomes part of it: they are united into one continuous piece of land (a shape drawn over existing land adds only what sticks out; a strip across the sea between two islands joins both; a join that encloses water makes a hole, a bay or lake-like gap, in the land). Corners snap to existing land as you draw, and when two neighbouring corners you click both lie on the coast of the same land the new shape follows that coast between them (the shorter way round), so it fits against it with no seam or sliver; on the server, corners that are almost on a neighbour's corner or border are put exactly on it before joining. *Reshape shapes* does the same when you drag land onto other land. Turn it off with the *Join land that overlaps or touches other land* checkbox (shown with the land tools) to keep pieces separate. The join is done by `lib/polygons.js`, a union of shapes with holes that I wrote and tested against thousands of random shapes (no outside library). Elevation follows: cells of the old shore that are now inland, and are still what plains made them (not edited by hand), rise to the interior's height; hand edits are kept.
- **Names for water.** Rivers and lakes can be named (optional) in the panel when selected: a river's name runs along it, a lake's sits in the middle of it. Seas and oceans are named with **Name a sea**: draw a loose outline around the water and give it a name; the name is lettered across the middle of the outline and sized to it (the outline is only shown in the editor, and can be reshaped like any shape). The *River, lake and sea names* layer switch hides them all.
- **Names scale with what they name, and fade as you zoom in.** A state's, superstate's, lake's or sea's name is sized from the width of what it names, so a big place has a big name; it grows with the map as you zoom, and once it is large it fades in proportion until it has disappeared, so a name never sits over the land it names. Too small to read, it is left out. Where names collide the bigger one wins (a superstate's name takes the place of its clients' names until you have zoomed in far enough for them to show). The fade distances are the constants at the top of the names section of `map-core.js`.
- **Statuses.** A state that is a client of a superstate can be its **capital state** (only one per superstate: choosing another moves it), a **province** (the default), **vassal**, **march** or **territory**; set it in the state's panel. The capital is marked with a star on the map, the statuses are shown in the clients list on the superstate's lore page, and a client's page and panel say, for example, "Capital state of Tanak Union". Taking a state out of its superstate (or moving it) resets it to province.
- **Statistics.** Each state's panel (and its lore page, under *On the map*) gives its approximate **area** in square miles, the length of its **border** in miles, and its **neighbours** with the length of border shared with each. They are measured off the shapes as drawn with the map's scale, rounded to two significant figures. A superstate is its clients together (its border is its outer border), and its neighbours are the nearest enclosing states that aren't part of it. Computed by `computeStats()` in `lib/maps.js`.
- **Coastline snapping.** While drawing a state (and when dragging a corner in *Edit borders*), clicks near the coast of a land shape snap onto it (lakes are ignored), and clicking two points on the same coast fills in the coast between them, the shorter way round, so a state can follow the shore exactly without spilling into the sea or leaving land uncovered. A neighbour's border and existing corners take priority over the coast, and it can be turned off with the *Snap to the coastline* checkbox. The coast is copied when you draw, so if you reshape the land later the states don't follow it.
- **Tracing.** Upload a PNG, JPEG or WebP as a *tracer image* and it is drawn under the map (land and lakes show through it while it is visible). Each map can have several, each with its own position and width/height (in map units), opacity and show/hide, so a big painted map can be traced a piece at a time. The first image on an empty map sets the map's size. Tracer images are only for editing: the files live in `data/map-images/` and are never published, so the public map is drawn from the vector shapes alone.
- **Scale.** *Set scale* measures two clicked points against a distance in miles you enter (or type "miles per map unit" in *Map settings*). The scale bar at the corner of the map shows a round number of miles and follows the zoom.
- **Places.** Cities and landmarks, optionally linked to a lore page.
- **Do not publish** works on maps, states, places and shapes. Hiding a map hides everything on it; hiding a state also withholds its lore page.
- **Not yet:** rivers and lakes that follow the elevation, merging or splitting the *shapes* of states (grouping, above, is separate), states that follow the land when it is reshaped, and dragging a tracer image with the mouse (use its position boxes).

Code: `lib/maps.js` (data and border logic), `routes/maps-api.js`, `routes/maps-pages.js`, `public/assets/maps/` (`map-core.js` shared drawing, `map-viewer.js` public page, `map-editor.js`).

## Public site and publishing

The program has two modes, set with environment variables (`lib/config.js`):

- **Editor** (the default): everything, read-write. This is your local copy. It also has a **Settings** page (the link in the slim top bar) with the Publish button.
- **Public** (`MODE=public`): read-only. There are no Editor tabs, the editor pages and scripts return 404, every request that isn't a plain read is refused (405), and the calendar shows notes without any way to add, edit, move or delete them. It never writes to its database; it only replaces it when you publish.

Run the two on separate machines and push your database from the editor to the public site. There are no accounts or logins.

**Do not publish.** Every language, dictionary entry, lore category, lore page, calendar note, map, map state, place and map shape has a **Do not publish** checkbox (off by default, so everything is published unless you mark it). Marked items stay here as normal (lists show a small crossed-out eye, or "not published" beside a language or category) and are left out of what is published. Marking a language or category leaves out the words or pages inside it, a note whose book is not published stays but is no longer assigned to that book, and links to something left out simply show as missing links. The Settings page lists exactly what the next publish will leave out. The hidden rows are deleted from a copy of the database *before it leaves this machine*, the search indexes are merged and the file is vacuumed, so the hidden text isn't in what is sent. (A visible page's own text is sent as written: if it mentions a hidden page by name, that name goes with it.)

**Setting it up**

1. On the public machine, start the program with a secret token, behind HTTPS (a reverse proxy such as Caddy or nginx; the program listens on `127.0.0.1` unless you set `HOST`):

   ```bash
   MODE=public PORT=3000 PUBLISH_TOKEN=<a long random string> node server.js
   ```

   A public instance runs under a small built-in supervisor: after a published database is swapped in, it restarts itself on the new data (a moment's downtime). It also works under systemd or Docker. `DATA_DIR` changes where its database lives (default `./data`).
2. Here, open **Settings**, enter the public site's address (`https://…`) and the same token (the **Generate** button makes a random one), and save. They are kept in `data/settings.json` on this machine only (not in git).
3. Press **Publish now**. Publishing again replaces what is online.

**How an upload is protected.** The token is never sent: the upload is signed with HMAC-SHA256 over a timestamp and the body, and the public side rejects bad signatures, timestamps more than five minutes off (so a captured upload can't be replayed), uploads that aren't healthy databases (an integrity check and a required-tables check), and oversized files. The new database is written beside the live one and swapped in; the previous one is kept as `worldbuilding.db.previous`. `eras.json` goes up with the database so the calendar and the era pages stay in step. Publishing needs `https://`, except to this machine itself. Code: `lib/publish.js`, `routes/settings.js`, `lib/visibility.js`.
